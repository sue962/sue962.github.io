실시간 비대면 공연 플랫폼 ‘덕타버스’ Duktaverse — Real-Time Virtual Performance Platform

가상 공간에서 여러 사용자가 대화하며 공연 영상을 볼 수 있는 플랫폼을 개발했습니다. 팀장으로 서버와 백엔드를 맡아 회원가입, 공연 예약, 실시간 접속, 음성 및 텍스트 대화, 영상 송출 기능을 연결했습니다. A service where sign-up, performance booking, dozens of simultaneous users, voice and text chat, and video streaming all had to run at once on the same screen. Each is buildable on its own; switched on together they interfere. My job was tying them into one system that held up end to end.

기능 분리

회원가입, 공연 예약, 실시간 접속, 음성 및 텍스트 대화, 영상 송출의 다섯 기능을 연결하는 플랫폼입니다. 코로나로 대학 행사가 취소되거나 온라인으로 바뀌던 시기에, 관객이 영상을 보면서 서로 대화하고 참여할 수 있는 공연장을 만들고자 했습니다. 저는 팀장으로 기획과 일정 관리, 시스템 설계를 맡고 서버와 백엔드, 데이터베이스를 구현했습니다.

The platform ties together five subsystems: sign-up, performance booking, live presence, voice and text chat, and video streaming. It began while university events were being cancelled or moved online, with the aim of a venue where an audience could watch together and still talk to each other. As team lead I owned planning, scheduling and system design, and built the server, backend and database.

5개 기능 영역 · 9개월 (기획 – 발표)

저장소 분리

회원 정보와 공연 예약은 MySQL에서 관리하고, 실시간 접속과 채팅은 Photon Server에서 처리했습니다. 영구 보관이 필요한 데이터와 접속 중에만 유지되는 상태는 성격이 다릅니다. 화면과 기능에 필요한 정보를 정리해 ERD를 작성하고 각 기능에서 무엇을 저장하고 조회할지 정한 뒤 데이터베이스를 만들었습니다.

Accounts and bookings live in MySQL while live presence and chat run on Photon Server, because data that must persist and state that exists only during a session are different things. An ERD was drawn from what the screens and features actually needed, and the database was built after deciding what each feature writes and reads.

MySQL 계정·예약 · Photon 접속·채팅

식별자 연결

두 서버가 같은 사용자를 같은 사람으로 인식해야 했습니다. 인증된 사용자의 식별 번호를 Photon에 전달해 로그인 계정과 가상 공간의 사용자를 연결했고, 채팅에서는 데이터베이스에 저장된 학번으로 발화자를 구분했습니다. 공연 예약도 같은 데이터베이스를 거쳐, 공연장에 들어갈 때 그 기록을 불러와 공연자와 관객을 구분합니다.

Both servers had to recognise the same user as the same person. An authenticated user's identifier is carried into Photon, linking the login account to the avatar in the space, and chat distinguishes speakers by the student number held in the database. Bookings pass through the same database, and entering the venue loads that record to separate performers from audience.

통합 테스트

개별 테스트에서 정상 작동하던 기능도 함께 실행하면 지연과 끊김이 생겼습니다. 기능별 동작을 확인한 뒤 실제 사용 순서대로 접속, 대화, 영상 관람을 이어서 해보며 연동 문제를 점검했습니다.

Features that behaved in isolation produced lag and dropouts once they ran together. After checking each on its own, the sequence was exercised in the order a real user follows: join, talk, watch, with integration problems caught along the way.

통합의 문제The integration problem

개별 테스트에서는 정상 작동하던 기능도 함께 실행하면 지연과 끊김이 발생했습니다. 다섯 기능을 동시에 사용하는 상황에서 문제를 확인했습니다.

Building each feature and running five of them at once turned out to be different jobs. Each worked alone; together they produced lag and dropouts.

  • 회원 계정과 실시간 접속 정보를 연결해야 했습니다. 회원 정보와 공연 예약은 MySQL에서 관리하고, 실시간 접속과 채팅은 Photon Server에서 처리했습니다. 로그인 계정과 공연장 안의 사용자가 일치하도록 연결했습니다.
  • Two different servers had to agree on who a user was. Accounts and bookings live in MySQL while live presence and chat run through Photon. If the two do not recognise the same person as the same person, the logged-in account and the character in the venue come apart.
  • 음성 채팅과 영상 송출을 함께 실행하면 지연이 생겼습니다. 각 서버의 역할과 통신 경로를 확인하며 지연과 끊김이 발생하는 부분을 조정했습니다.
  • Voice and video competed for the same path. Running voice chat and video streaming together introduced lag and dropouts, so I worked through what each server was responsible for and which route each stream took, adjusting as I went.
  • 다섯 기능을 동시에 켜고 테스트했습니다. 개별 기능의 동작을 확인한 뒤 실제 사용 순서대로 접속, 대화, 영상 관람을 이어가며 연동 문제를 점검했습니다.
  • Passing feature-level tests was not enough. Nothing counted as done until it had been checked again with all five running at once — the failures almost always sat between the features rather than inside them.

서버 · 데이터베이스 설계Server and database

  • 회원 정보와 공연 예약 데이터를 설계했습니다. 화면과 기능에 필요한 정보를 정리해 ERD를 작성했습니다. 각 기능에서 어떤 데이터를 저장하고 조회할지 정한 뒤 데이터베이스를 만들었습니다.
  • I started from the data the service actually needed. Working out what each screen and feature required, I drew the ERD and then built the database — settling where account and booking data would be written and where it would be read before writing any of it.
  • AWS EC2에 서버를 올렸습니다. Nginx와 PHP, MySQL을 설치하고 인바운드 규칙을 설정해 외부에서 접근할 수 있게 했습니다. 로그인과 회원가입 요청이 들어오면 데이터베이스에서 사용자 정보를 조회해 대조합니다.
  • The server ran on AWS EC2 with Nginx, PHP and MySQL, and inbound rules opened for external access. Sign-up and login requests are checked against the account records in the database.
  • 인증된 사용자의 식별 번호를 Photon에 전달했습니다. 이 번호로 회원 계정과 가상 공간의 사용자를 연결했습니다. 채팅에서는 데이터베이스에 저장된 학번으로 발화자를 구분했습니다.
  • Authenticated users receive an identifier that is handed to Photon — the link between the two servers. It distinguishes who is who inside the live space, and chat identifies speakers by their student number from the database.
  • 공연 예약도 같은 데이터베이스를 거칩니다. 사용자가 신청한 공연 정보를 저장하고, 공연장에 들어갈 때 그 기록을 불러와 공연자와 관객을 구분합니다.
  • Bookings go through the same database. A submitted booking is stored and then read back on entry to the venue to tell performer from audience.
  • 별도 프로젝트에서 영상 송출 기능을 먼저 구현했습니다. YouTube API 연결을 확인한 뒤 본 프로젝트에 추가했습니다. 공연자가 스트리밍 주소를 입력하면 플랫폼 안에서 해당 영상을 함께 볼 수 있도록 했습니다.
  • Video streaming was built outside the main project first. Working directly in the live project risked breaking what already worked, so I got the API connection running in an empty project and only then moved it across. A performer enters a YouTube stream URL and the video plays inside the platform for everyone.

두 서버를 잇는 경로How the two servers connect

AWS EC2 · Photon

사용자 인증 후 받은 식별 번호를 Photon에 전달해 로그인 계정과 가상 공간의 캐릭터를 연결했습니다. Authentication finishes in MySQL, but the identifier it returns has to travel with the user into Photon for the venue to tell people apart. Break that link and the logged-in account and the character become two different people.

팀 운영Running the team

  • 주 2회 회의에서 진행 상황과 Git 커밋을 확인했습니다. 팀원들과 구현이 막힌 부분을 점검하고, 서버와 데이터베이스를 화면 및 가상 공간에 연결하는 순서를 조율했습니다.
  • Progress was tracked through twice-weekly meetings and the Git history. Rather than relying on verbal status, we looked at the commits together to see where things were actually stuck, and I sequenced my server and database work so it could meet the screens and spaces the others were building.
  • 캐릭터 구현에 어려움을 겪던 팀원과 제작 방법을 찾아봤습니다. 기능 축소를 고민하던 팀원과 제작 도구를 함께 공부했습니다. 교수님께 요청해 해당 분야 실무자의 자문을 받고 구현 문제를 해결했습니다.
  • When someone was stuck, I asked what was happening first. The member handling 3D character work considered cutting the feature because it would not come together. Before arguing to keep it, I checked that they wanted a good result too and simply could not find the way — then we learned the tool together and, through our supervisor, got advice from a practitioner in that field to get past it.
  • 중간에 추가된 영상 송출 기능은 자료 조사를 나눠 맡았습니다. 팀원들과 구현 방법을 조사하고, 모델링이 끝나는 시점에 맞춰 기능을 통합했습니다.
  • A late feature was split across the team. Video streaming was added midway, with the remaining schedule under pressure. Instead of absorbing it alone, we divided the research and then merged the feature in once the venue modelling was finished.
