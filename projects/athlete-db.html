담당 범위Scope

선수, 선발전, 심판, 장비, 의료 패키지, 여행 지원금을 다루는 데이터베이스입니다. 설계는 팀에서 함께 했고, 제가 맡은 부분은 데이터 모델 검토와 DDL·DML 작성, PostgreSQL 저장 함수, 그리고 Python 조회 계층입니다.

A database covering athletes, trials, officials, equipment, medical packages and travel stipends. I worked on the data model review, the DDL and DML, the SQL stored functions, and the Python query layer.

이 프로젝트에서는 새로 만드는 일보다 이미 있는 정의를 요구사항과 맞춰보는 데 시간을 더 썼습니다. 설계 초안도, 넘겨받은 스키마도 그대로 쓰지 않고 먼저 검증했습니다. Most of my work here was not adding features but checking whether existing definitions actually matched the requirements. Neither the draft design nor the schema was taken as given.

AI 설계 초안 검증Auditing the AI-generated draft

초기 개념 설계는 생성형 AI가 만든 ERD였습니다. 읽어보면 그럴듯했는데, 요구사항과 하나씩 대조하자 네 영역에서 문제가 나왔습니다. 각각 요구사항의 어느 문장과 어긋나는지까지 달아서 정리했습니다.

The initial conceptual design was an ERD produced by a generative AI. It looked plausible, but checking it against the requirements surfaced problems in four areas — each written up with the specific requirement it contradicted.

  • 엔터티와 속성이 축약돼 있었습니다. 선수가 Name과 Contact Details로 뭉개져 있었지만 도메인은 이름·성·휴대폰·이메일·고유 여권번호를 각각 요구했습니다. 아마추어는 소속 클럽만 있고 클럽 위치가 빠졌고, 의료 패키지에는 요구사항에 없는 PackageID와 Cost가 추가로 생겨 있었습니다. 장비는 제조사·모델·연식·상태 등급이 모두 누락됐습니다.
  • Entities and attributes were flattened. The athlete was reduced to a name and contact details, where the domain called for first name, last name, mobile, email and a unique passport number separately. Amateur had a training club but no club location, and Medical Package had gained a PackageID and Cost the requirements never mentioned. Equipment was missing manufacturer, model, year and condition rating entirely.
  • 관계의 다중성이 틀렸습니다. 참가 관계가 1:N으로 되어 있었지만, 한 선수가 여러 경기에 나가고 한 경기에 여러 선수가 참가하므로 다대다여야 했습니다. 경기 기록(PerformanceData)도 경기가 아니라 참가 관계에 두어야 특정 선수의 특정 경기 결과를 표현할 수 있었습니다. 심판 관계도 한 경기에 여러 심판이 배정될 수 있는데 1:N으로 제한돼 있었고, 한 경기의 우승자는 한 명이라는 규칙은 아예 빠져 있었습니다.
  • Relationship cardinalities were wrong. Participation was modelled 1:N, but an athlete competes in many trials and a trial involves many athletes, so it had to be many-to-many — and performance data belongs on the participation, not on the trial, to express one athlete's result in one trial. Officials were likewise capped at one per trial when the domain allows several, and the rule that a trial has a single winner was missing altogether.
  • 식별 방식이 불완전했습니다. 여행 지원금은 선수와 계약일의 조합으로 식별되는데, 초안은 계약일 자체를 빠뜨려서 식별할 근거가 없었습니다. 지원금만으로는 식별이 안 되고 선수에 기대야 하는 구조인데, 그게 초안에는 보이지 않았습니다.
  • Identification was incomplete. A travel stipend is identified by the athlete together with the signing date, but the draft omitted the signing date entirely — leaving nothing to identify it by, and hiding the fact that its identity depends on another entity.
  • 제약이 사라져 있었습니다. 빠진 규칙은 다섯 가지입니다. 선수는 전문과 아마추어 중 하나에만 속한다, 전문 선수는 의료 패키지를 1개에서 5개까지 골라야 한다, 아마추어는 그 패키지를 쓸 수 없다, 하루에 한 경기만 참가할 수 있다, 상태가 good 이상인 장비만 쓸 수 있다. 초안에는 이 중 어느 것도 들어 있지 않았습니다.
  • Constraints had quietly vanished. That the specialization into professional and amateur is total and disjoint, that professionals must select between one and five medical packages, that amateurs cannot access them, the one-event-per-day rule, and the rule that only equipment rated good or better may be used — none of these survived into the draft.

성적은 ‘그 경기의 기록’이 아니라 ‘그 선수가 그 경기에서 낸 기록’입니다. 초안처럼 경기에 두면 선수별로 구분할 수 없어, 참가 기록으로 옮기고 선수 ID와 경기 ID를 묶어 기본키로 지정했습니다. A result is not “the trial's record” but “this athlete's record in this trial”. Attached to the trial, as in the draft, it cannot be told apart per athlete — so it moved onto the participation record, keyed on athlete ID and trial ID together.

AI가 만든 결과는 문장이 자연스럽고 형식도 맞았기 때문에, 빠진 것을 찾으려면 결과물이 아니라 요구사항에서 출발해야 했습니다. 요구사항의 각 규칙을 체크리스트로 만들어 하나씩 대조하는 방식으로 검토했습니다.

The AI output read naturally and had the right shape, which is exactly why finding what was missing meant starting from the requirements, not from the output. I turned each stated rule into a checklist item and worked through them one at a time.

설계 결정Design decisions

  • 성적은 경기가 아니라 참가 기록에 있습니다. 선수와 경기를 다대다 연결 테이블로 두고, 선수 ID와 경기 ID를 묶어 복합 기본키로 지정했습니다. 성적은 특정 선수가 그 경기에서 낸 결과이므로, 두 식별자가 함께 있어야 식별됩니다.
  • Results live on the participation record, not the trial. Athletes and trials are joined through a junction table whose primary key is the athlete ID and trial ID together — a result belongs to one athlete in one trial, so it takes both identifiers to identify it.
  • 우승 테이블의 기본키는 경기 ID 하나입니다. 한 경기에 우승자가 두 명 등록되는 상황을 애초에 만들 수 없게 하려고 이렇게 두었습니다. 애플리케이션 검사에 맡기지 않고 구조로 막았습니다.
  • The wins table is keyed on the trial alone. Making the trial ID the primary key means two winners for one trial cannot be recorded in the first place — the rule is enforced by structure rather than by an application check.
  • 여행 지원금은 약한 엔터티이고, 최종 금액은 생성 열입니다. 선수 ID와 계약일을 복합 기본키로 두어 같은 선수의 계약을 날짜별로 구분하고, 기본 지원금·보너스·숙박비를 각각 저장했습니다. 최종 지급액은 저장하는 대신 GENERATED ALWAYS AS (Base + Bonus - COALESCE(Housing, 0)) STORED로 계산되게 해, 원본 금액이 바뀌었는데 최종액만 남아 생기는 불일치를 없앴습니다.
  • The travel stipend is a weak entity with a generated total. Athlete ID plus signing date forms the composite key, separating one athlete's contracts by date, and base, bonus and housing amounts are each stored. The final figure is not stored but computed as GENERATED ALWAYS AS (Base + Bonus - COALESCE(Housing, 0)) STORED, so it can never drift from the components it is derived from.
  • 여권번호에는 UNIQUE 제약을 적용했습니다. 내부 식별자인 선수 ID를 기본키로 두되, 외부 식별자인 여권번호는 중복될 수 없는 값이므로 별도 제약으로 구분했습니다.
  • Passport numbers carry a UNIQUE constraint. The athlete ID stays the internal primary key, while the passport number — an external identifier that cannot repeat — is constrained separately.
  • 값의 범위는 CHECK으로 제한했습니다. 장비 상태는 poor · fair · good · very good · excellent 다섯 값만, 후원금 종류는 세 가지 값만 허용되도록 스키마에 직접 넣었습니다.
  • Value domains are restricted with CHECK. Equipment condition accepts only poor, fair, good, very good and excellent; sponsorship payments only the three permitted types — both declared in the schema itself.
  • 키와 외래키만으로 표현할 수 없는 규칙은 트리거로 구현했습니다. "하루에 한 경기만 참가"는 참가 기록과 경기 날짜를 함께 봐야 판정할 수 있으므로, 참가 기록을 추가하거나 변경할 때 같은 날짜의 다른 경기 참가 여부를 조회하는 트리거를 작성했습니다. 전문 선수의 의료 패키지 1~5개 제한도 같은 방식으로 처리했습니다.
  • Rules that keys cannot express became triggers. "One event per day" can only be judged by looking at the participation record together with the trial date, so inserting or updating a participation checks for another trial on the same date. The one-to-five medical package limit for professionals is handled the same way.

Athlete

선수의 기본 정보입니다. 초안에서 ‘이름’과 ‘연락처’로 뭉쳐 있던 것을 이름·성·휴대폰·이메일로 나누고, 여권번호를 별도 속성으로 두었습니다. 내부 식별자는 AthleteID이고, 외부 식별자인 여권번호는 중복될 수 없으므로 UNIQUE로 구분했습니다.

The athlete's core record. What the draft had flattened into “name” and “contact details” is split into first name, last name, mobile and email, with the passport number as its own attribute. AthleteID is the internal identifier; the passport number, being an external one, is constrained UNIQUE.

PRIMARY KEY AthleteID · UNIQUE PassportNumber

Amateur

아마추어 선수의 하위 유형입니다. 소속 훈련 클럽과 클럽 위치를 함께 보관합니다. 초안은 클럽만 두고 위치를 빠뜨렸습니다. 아마추어는 의료 패키지를 선택할 수 없습니다.

The amateur subtype, holding the training club together with its location — the draft had the club but dropped the location. Amateurs cannot select medical packages.

PRIMARY KEY AthleteID → Athlete · ON DELETE CASCADE

Professional

전문 선수의 하위 유형입니다. 선수는 아마추어와 전문 중 정확히 하나에 속합니다(전체이자 배타적). 의료 패키지 선택은 이 유형에서만 가능하도록 외래키를 Professional에 걸었습니다.

The professional subtype. Every athlete belongs to exactly one subtype — the specialization is total and disjoint — and medical package selection is restricted to this one by pointing that foreign key at Professional rather than Athlete.

PRIMARY KEY AthleteID → Athlete · ON DELETE CASCADE

AthleteImage

선수당 여러 장일 수 있는 이미지입니다. 다중값 속성이므로 선수 테이블에 컬럼으로 넣지 않고 분리했고, 선수 ID와 이미지 URL을 묶어 기본키로 두어 같은 이미지가 중복 등록되지 않게 했습니다.

Images, of which an athlete may have several. A multivalued attribute does not belong in a column on the athlete row, so it lives here — keyed on athlete ID and image URL together, which also stops the same image being registered twice.

PRIMARY KEY (AthleteID, ImageURL)

TravelStipend

약한 엔터티입니다. 지원금 자체의 식별자가 없고 선수와 계약일의 조합으로 식별되므로, 두 값을 복합 기본키로 두어 같은 선수의 계약을 날짜별로 구분했습니다. 초안은 계약일을 빠뜨려 식별 근거가 없었습니다.

A weak entity: a stipend has no identifier of its own and is identified by the athlete together with the signing date, so both form the composite key, separating one athlete's contracts by date. The draft omitted the signing date, leaving nothing to identify it by.

기본 지원금·보너스·숙박비를 각각 저장하고 최종 지급액은 저장하지 않습니다. 생성 열로 계산되게 해, 원본 금액이 바뀌었는데 최종액만 예전 값으로 남는 상황을 없앴습니다.

Base, bonus and housing amounts are each stored; the final figure is not. Computing it as a generated column means it can never be left holding a stale value after its components change.

PRIMARY KEY (AthleteID, SigningDate) · FinalStipend GENERATED ALWAYS AS (Base + Bonus − COALESCE(Housing, 0)) STORED

SponsorshipPayment

선수가 받은 후원금 기록입니다. 종류는 기업 후원·정부 지원금·개인 기부 세 가지만 허용되도록 CHECK 제약을 걸었습니다.

Sponsorship received by an athlete. A CHECK constraint limits the type to corporate sponsorship, government grants or private donations.

PRIMARY KEY PaymentID · CHECK PaymentType ∈ (corporate sponsorship, government grants, private donations)

Equipment

장비 기록입니다. 초안에는 이름과 모델만 있었지만 요구사항은 제조사·연식·기계적 상태·상태 등급까지 요구했습니다. 등급은 다섯 값만 허용하도록 제한했고, 사용 가능 여부(good 이상)를 이 값으로 판정합니다.

Equipment records. The draft carried only a name and model, where the requirements also called for manufacturer, year, mechanical condition and a condition rating. The rating is restricted to five values, and usability (good or better) is judged from it.

선수가 삭제돼도 장비 기록 자체는 남아야 하므로, 외래키를 ON DELETE SET NULL로 두어 소유자만 비우도록 했습니다.

Equipment should survive the deletion of its owner, so the foreign key is ON DELETE SET NULL — clearing the owner rather than removing the record.

PRIMARY KEY EquipmentName · CHECK Condition ∈ (poor, fair, good, very good, excellent) · ON DELETE SET NULL

ParticipatesIn

선수와 경기를 잇는 다대다 연결 테이블이며, 성적이 여기에 있습니다. 성적은 특정 선수가 그 경기에서 낸 결과이므로, 선수 ID와 경기 ID가 함께 있어야 식별됩니다.

The many-to-many junction between athletes and trials — and where the result lives. A result belongs to one athlete in one trial, so it takes both identifiers to identify it.

‘하루에 한 경기만 참가’ 규칙은 참가 기록과 경기 날짜를 함께 봐야 판정할 수 있어, 삽입·갱신 시 같은 날짜의 다른 경기 참가 여부를 조회하는 트리거로 구현했습니다.

The one-event-per-day rule can only be judged by reading the participation together with the trial date, so a trigger checks for another trial on the same date on insert and update.

PRIMARY KEY (AthleteID, TrialID) · TRIGGER one event per day

Wins

경기별 우승자입니다. 기본키를 경기 ID 하나로 두었기 때문에, 한 경기에 우승자가 두 명 등록되는 일이 구조적으로 불가능합니다. 애플리케이션 검사에 맡기지 않고 스키마에서 막았습니다.

The winner of each trial. Because the primary key is the trial ID alone, recording two winners for one trial is structurally impossible — blocked by the schema rather than by an application check.

초안에는 이 규칙 자체가 빠져 있었습니다.

This rule was absent from the draft entirely.

PRIMARY KEY TrialID · FK AthleteID → Athlete

Oversees

심판과 경기를 잇는 다대다 연결입니다. 요구사항은 한 경기를 최소 한 명 이상의 심판이 담당한다고 했으므로 여러 명이 배정될 수 있어야 하는데, 초안은 심판 한 명이 여러 경기를 담당하는 1:N으로 제한하고 있었습니다.

The many-to-many junction between officials and trials. The requirement is that a trial is overseen by at least one official, which allows several — but the draft capped it at one official per trial.

PRIMARY KEY (OfficialID, TrialID)

Selects

전문 선수와 의료 패키지를 잇는 다대다 연결입니다. 외래키가 Athlete가 아니라 Professional을 가리키도록 해, 아마추어가 패키지를 선택하는 것 자체가 불가능합니다.

The many-to-many junction between professionals and medical packages. The foreign key points at Professional, not Athlete, so an amateur selecting a package is impossible by construction.

1~5개 선택 제한은 개수를 세어야 판정할 수 있으므로 트리거로 구현했습니다.

The one-to-five limit requires counting, so it is implemented as a trigger.

PRIMARY KEY (AthleteID, PackageName) → Professional · TRIGGER 1–5 packages

수정 내역What I changed

‘완료된 경기’의 날짜 기준이 두 군데에서 달랐습니다“Completed” meant two different things in two places

전Before trials_completed … < CURRENT_DATE last_trial_date … <= CURRENT_DATE
후After trials_completed … < CURRENT_DATE last_trial_date … < CURRENT_DATE

완료 경기 수는 오늘을 제외하고, 최근 경기일은 오늘을 포함하고 있었습니다. 둘 다 ‘완료’를 뜻하는데 기준이 달라, 같은 선수의 요약에서 두 숫자가 어긋날 수 있었습니다. 오늘 이전을 기준으로 통일했습니다. The completed-trial count excluded today while the last-trial date included it. Both meant “completed”, so one athlete's summary could disagree with itself. Both now cut off before today.

국적이 비어 있으면 쉼표만 남았습니다A missing nationality left a stray comma

전Before COALESCE(A.NATIONALITY, '') || ', ' || … → "Jane Doe, , Professional"
후After COALESCE(A.NATIONALITY, 'Unknown') || ', ' || … → "Jane Doe, Unknown, Professional"

빈 문자열로 대체하면 문자열을 이어붙일 때 쉼표가 연달아 남아, 값이 없다는 사실이 아니라 형식이 깨진 것처럼 보입니다. 없음을 명시적으로 표시하도록 바꿨습니다. Substituting an empty string leaves doubled-up commas once the parts are concatenated, so a missing value reads as broken formatting instead of absence. It now says so explicitly.

화면에 보이는 값으로는 검색이 되지 않았습니다What you saw on screen could not be searched

전Before 표시: COALESCE(…, 'N/A') 검색: COALESCE(…, '') ILIKE …
후After 표시: COALESCE(…, 'N/A') 검색: COALESCE(…, 'N/A') ILIKE …

기록이 없는 행은 화면에 ‘N/A’로 보이는데, 검색은 빈 문자열을 기준으로 하고 있어 ‘N/A’로 검색하면 아무것도 나오지 않았습니다. 표시와 검색이 같은 값을 쓰도록 맞췄습니다. Rows with no note displayed as “N/A”, but the search compared against an empty string — so searching “N/A” returned nothing. Display and search now use the same value.

‘같은 날짜에 같은 이름의 경기는 하나’라는 규칙을 DB가 지키지 않았습니다“One trial per name and date” was not enforced by the database

전Before — 제약 없음 애플리케이션에서 중복 여부를 검사
후After CREATE UNIQUE INDEX unique_trial_name_date ON TRIALS (LOWER(TRIAL_NAME), TRIAL_DATE);

요구사항은 같은 날짜에 해당 경기가 있으면 재사용하고 없으면 새로 만들라고 했지만, 중복 생성을 막는 제약이 없어 전적으로 애플리케이션 검사에 의존했습니다. 이름을 소문자로 비교하는 유니크 인덱스를 추가해 대소문자만 다른 중복까지 데이터베이스가 막도록 했습니다. The requirement was to reuse an existing trial for that date or create a new one, but nothing in the database prevented duplicates — it all rested on an application check. A unique index comparing the name in lower case now blocks duplicates, including ones differing only in case.

금액이 Python에서 Decimal로 전달됐습니다Amounts arrived in Python as Decimal

전Before SPONSORSHIP NUMERIC COALESCE(SS.SPONSORSHIP, 0) AS SPONSORSHIP → Decimal('3000.00')
후After SPONSORSHIP FLOAT8 COALESCE(SS.SPONSORSHIP, 0)::FLOAT8 AS SPONSORSHIP → 3000.0

NUMERIC은 Python에서 Decimal 객체로 전달돼 그대로 출력하면 Decimal('3000.00')처럼 보입니다. 데이터베이스가 내주는 자료형이 화면까지 의도한 형태로 전달되도록 반환 시점에 변환했습니다. NUMERIC reaches Python as a Decimal object, which prints as Decimal('3000.00') if passed straight through. Converting at the point of return keeps the type the database hands back usable all the way to the screen.

도달할 수 없는 분기와 중복된 조건이 남아 있었습니다An unreachable branch and a repeated condition

전Before CASE … ELSE 'Unknown' END ORDER BY CASE WHEN P_SEARCH… IS FALSE THEN … END, CASE WHEN P_SEARCH… IS FALSE THEN … END, CASE WHEN P_SEARCH… IS FALSE THEN … END
후After CASE … END ORDER BY CASE WHEN T.TRIAL_DATE >= CURRENT_DATE THEN 0 ELSE 1 END ASC, T.TRIAL_DATE ASC, T.TRIAL_NAME ASC

제약상 모든 선수는 아마추어 또는 전문으로 분류되므로 ‘Unknown’ 분기에는 도달할 수 없었습니다. 정렬절도 같은 조건을 세 번 반복하고 있어, 실제로 필요한 기준만 남겼습니다. A constraint already forces every athlete into amateur or professional, so the “Unknown” branch could never be reached. The ordering clause repeated the same condition three times; only the criteria that do work remain.

조회 계층Query layer

Python에서 PostgreSQL 저장 함수를 호출해 로그인, 선수별 선발전 요약, 선발전 검색, 참가 등록, 결과 갱신 다섯 기능을 구현했습니다. 여기서도 데이터베이스가 내준 값이 코드와 화면에서 같은 뜻으로 쓰이는지를 계속 봤습니다.

Five functions call PostgreSQL stored functions from Python: login, per-athlete trial summary, trial search, registering a participation, and updating a result. The same standard applied here — whether the value the database returns keeps its meaning in the code and on screen.

  • 결과를 순서가 아니라 컬럼 이름으로 읽도록 바꿨습니다. 처음에는 row[0], row[1]처럼 위치로 읽고 있어서, 뷰의 컬럼 순서가 바뀌면 조용히 잘못된 값이 들어갑니다. 커서의 컬럼 정보를 이용해 이름으로 매핑하도록 고쳤습니다.
  • Rows are read by column name instead of position. The original code indexed row[0], row[1] and so on, which silently yields wrong values the moment a view's column order changes. It now maps results by name using the cursor's column metadata.
  • SELECT *를 명시적인 컬럼 목록으로 바꿨습니다. 같은 이유로, 가져오는 컬럼이 질의문에 드러나 있어야 뷰가 변경될 때 영향 범위를 알 수 있습니다.
  • SELECT * became an explicit column list, for the same reason: what is being fetched has to be visible in the query for the impact of a view change to be traceable.
  • 경기 생성은 하나의 트랜잭션으로 묶었습니다. 모든 경기는 참가 기록과 심판 배정이 각각 최소 하나씩 있어야 한다는 트리거가 걸려 있어, 새 경기를 만들 때 세 행이 같은 트랜잭션에서 함께 들어가지 않으면 전체가 실패합니다. 이 조건을 먼저 파악하고 호출 순서를 맞췄습니다.
  • Creating a trial happens in one transaction. Triggers require every trial to have at least one participation row and one official assignment, so a new trial only succeeds if all three rows are inserted together. I worked that constraint out first and ordered the calls accordingly.
  • 입력 검증과 커서 정리를 추가했습니다. 값이 비었거나 공백뿐인 입력을 질의 전에 걸러내고, 예외가 나더라도 커서가 닫히도록 정리 경로를 명시했습니다.
  • Input validation and cursor cleanup were added — empty or whitespace-only input is rejected before a query runs, and cursors are closed on the failure path as well as the success one.
