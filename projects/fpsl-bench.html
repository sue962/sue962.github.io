LLM 개인화 연구 평가 벤치마크 Evaluation Benchmark for Personalized LLM Research

연합학습으로 개인 문체를 학습시키는 연구에서 평가 코드를 개발했습니다. 실험마다 달랐던 결과 파일 형식을 통일하고, 평가 지표와 데이터 누수를 자동으로 검사하도록 했습니다. I developed evaluation code for a study of personal writing styles in federated learning. I standardised the output formats across experiments and automated checks on metrics, schemas and data leakage.

담당 범위Scope

저자 50명의 글을 클라이언트로 나눠 연합학습으로 개인 문체를 학습시키고, 학습한 모델이 그 사람처럼 쓰는지 재는 연구입니다. 저는 평가 벤치마크 구현과 자동 검증 파이프라인, 산출물 표준화를 맡았습니다.

The study splits the writing of 50 authors across clients, trains a personal voice through federated learning, and measures whether the trained model writes like that person. I built the evaluation benchmark, the automated verification pipeline and the artifact standardization.

제가 개발한 FPSL-Bench는 연구의 표준 평가 방식으로 사용됐습니다. 모델의 학습 결과를 같은 지표와 파일 형식으로 비교할 수 있도록 했습니다. FPSL-Bench became the study’s standard evaluation. I implemented the metrics and file formats used to compare model outputs across experiments.

기존 평가 방식의 문제Every run produced a different shape

  • 같은 수치가 다른 이름으로 저장됐습니다. 실험을 돌릴 때마다 결과 파일의 컬럼 이름과 구조가 조금씩 달라서, 두 실험을 나란히 놓고 비교하려면 매번 사람이 맞춰야 했습니다.
  • The same number was stored under different names. Column names and structures drifted between runs, so comparing two experiments meant reconciling them by hand every time.
  • 하나의 유사도 지표에 서로 다른 평가 기준이 섞여 있었습니다. 저자의 평소 문체를 따르는 정도와 특정 예시의 정답에 가까운 정도를 같은 수치로 보고해, 각각을 구분하기 어려웠습니다.
  • It was unclear which question a metric answered. One similarity score was used to mean both “does this match the author's usual voice?” and “is this close to the held-out target for this example?” — two questions whose answers can diverge, reported as one number.
  • 데이터 누수 여부를 매번 수동으로 확인했습니다. 학습, 검증, 평가 데이터의 중복 여부와 평가 프롬프트의 원문이 학습 데이터에 포함됐는지를 눈으로 대조해야 했습니다.
  • Leakage checking rested on a person remembering to do it. Whether train, validation and test had stayed separate, and whether source texts referenced by prompts had leaked into training, was verified by eye each time.

평가 축 설계Splitting it into five questions

평가 기준을 다섯 축으로 나누고, 34개 지표를 각각 하나의 축에 배정했습니다. 지표별로 무엇을 측정하는지 구분하고, 소속 축을 스키마 파일에 기록해 코드에서 확인하도록 했습니다.

I split what we wanted to measure into five questions, with the rule that a metric belongs to exactly one of them. A metric serving two questions makes a rising score impossible to explain. All 34 metrics were assigned to a single axis, and that assignment lives in a schema file the code reads.

축을 클릭하면 그 축이 답하는 질문과 지표가 나타납니다 Click an axis to see the question it answers and the metrics under it

축을 선택하면 그 축이 답하는 질문과 지표가 표시됩니다. Select an axis to see the question it answers and its metrics.

모델 출력Model output

학습한 모델이 생성한 응답을 다섯 축으로 평가합니다. 평가 프롬프트 23개와 공개 원문 10개는 v0.1에서 고정하고 이후 버전에서도 유지했습니다.

What the trained model wrote in response to an evaluation prompt. Each piece of writing passes through all five questions. The 23 evaluation prompts and 10 public source texts were frozen in v0.1 and left untouched in later versions.

50 authors · 23 prompts · 10 source texts · non-IID Gini 0.11 / 0.20 / 0.43

A · 과거 글과의 일치History alignment

모델 응답이 저자의 평소 문체와 얼마나 비슷한지 측정합니다. 저자가 이전에 쓴 글 전체를 비교 기준으로 사용합니다.

Is the model writing the way this author habitually writes? Judged against the author's whole body of past writing rather than against one correct answer.

출력을 저자의 과거 글 중심점과 견준 유사도, 저자 50명 가운데 맞는 저자가 몇 번째로 가까운지의 순위, 맞는 저자와 나머지 저자 사이의 간격을 지표로 뒀습니다. 순위와 간격을 함께 보는 이유는, 모두와 비슷해져서 유사도가 올라가는 경우를 걸러내기 위해서입니다.

Metrics include similarity to the centroid of the author's history, where the correct author ranks among all 50 by distance, and the margin between the correct author and the rest. Rank and margin are read together to catch a score that rises because the output has become similar to everyone.

hist_align_* · 9 metrics

B · 정답 예시와의 유사도Target similarity

특정 평가 예시에 대해 모델 응답과 저자가 쓴 정답 글을 비교합니다. 평소 문체를 측정하는 A축과 구분해 예시별 유사도를 확인합니다.

For this one test example, how close is the output to what the author actually wrote? Unlike A, the question is tied to a single example.

A와 B를 나눠 둔 이유는 두 답이 어긋날 수 있기 때문입니다. 평소 문체는 잘 따라가면서 이번 예시의 정답과는 멀 수 있고, 그 반대도 가능합니다. 한 숫자로 합치면 어느 쪽인지 알 수 없습니다.

A and B are separated because they can disagree: an output can track the author's usual voice while sitting far from this particular target, or the reverse. Collapsed into one number, there is no telling which.

target_sim_* · 7 metrics

C · 저자 간 구분 가능성Group separability

학습 후에도 저자별 문체가 구분되는지 측정합니다. 여러 저자의 모델이 비슷한 문체로 응답하는 문체 동질화 현상을 확인하기 위한 축입니다.

This axis measures whether authors’ styles remain distinguishable after training. It checks for style homogenisation, where models for different authors produce increasingly similar writing.

저자별 점수와 함께 저자 간 문체 거리도 측정해, 학습 후 문체가 서로 비슷해졌는지 확인합니다.

Per-author scores alone will not reveal homogenization; it only shows up when the distance between authors is measured on its own.

group_sep_* · 8 metrics

D · 어시스턴트 말투로의 이동Assistantness drift

모델 응답이 저자의 문체보다 기본 어시스턴트의 말투에 가까워졌는지 측정합니다. 다른 문체 평가와 구분해 별도 축으로 기록합니다.

Has the output slid back into the default assistant register? Measured separately from the others, this tracks the model drifting toward the polite, uniform voice it started with.

C와 비슷해 보이지만 다릅니다. C는 저자들이 서로 구분되는지를 보고, D는 어느 한 방향(어시스턴트 말투)으로 쏠렸는지를 봅니다. 평가 프롬프트에는 이 쏠림을 유도하는 조건을 따로 표시해 두고 결과를 나눠 봤습니다.

Close to C but not the same: C asks whether authors differ from each other, D asks whether they have all moved in one particular direction. Prompts that invite that drift are tagged in the suite so results can be broken out by it.

assist_* · 4 metrics

E · 유용성 · 사실성 · 품질Utility, faithfulness & quality

응답의 유용성, 사실성, 문장 품질을 평가합니다. 문체가 비슷하더라도 문장이 부자연스럽거나 원문에 없는 내용이 추가됐는지 확인합니다.

Even with the voice preserved, is the writing still useful and coherent? Identity metrics alone miss this — it catches output that degenerates, or adds content the source never had, while style scores climb.

faith_* · qual_* · mauve · 6 metrics

표준 산출물Standard artifact

다섯 축의 평가 결과를 예시별로 한 파일에 저장합니다. 지표 이름, 자료형, 소속 축을 스키마로 통일해 다른 실험의 결과와 비교할 수 있도록 했습니다.

Metrics from all five axes are written per example into one file. Names, types and the axis each belongs to are fixed by schema, so results from different runs line up directly.

산출물은 모두 8종이고 각각 JSON Schema가 있습니다. 실행이 끝나면 검사 스크립트가 결과 파일을 스키마와 대조합니다.

There are eight artifact types, each with its own JSON Schema, and a validation script checks every output file against them once a run finishes.

generations · per_example_metrics · summary_metrics · breakdown ×3 · training_budget · quality_filter_report

자동 검사 9종Moving the checks into code

매번 눈으로 확인하던 항목을 검사 스크립트로 만들고, 한 번에 돌리는 통합 검사기로 묶었습니다. 모두 9종입니다.

What had been verified by eye became scripts, gathered under one runner. Nine checks in all.

In the leakage check, three of five sub-checks passed and two could not run without server-side data. Rather than recording that as a pass, the report says passed with skips and names what could not be run and why. Not having checked is not the same as having passed.

산출물 표준화Standardizing the artifacts

결과 파일의 형식The shape of a result file

전Before 실험마다 컬럼 이름·구조가 다름 지표가 어느 질문에 속하는지 불명확 비교하려면 사람이 매번 맞춤
후After 8종 산출물 × JSON Schema 지표 34개 → 축 1개에 배정 (스키마에 명시) validate_artifacts.py 가 실행 후 대조

산출물 8종에 각각 JSON Schema를 두고, 실행이 끝나면 결과 파일이 스키마를 따르는지 검사하도록 했습니다. 지표가 어느 축에 속하는지도 사람이 기억하는 대신 스키마에 적어 두고 코드가 읽게 했습니다. Each of the eight artifact types has a JSON Schema, and a run ends by checking its output against them. Which axis a metric belongs to is written in the schema and read by code, rather than remembered by a person.

  • v0.1의 평가 조건과 파일을 고정했습니다. 클라이언트 구성, non-IID 배분 3종, 평가 프롬프트 23개, 공개 원문 10개, 디코딩 설정을 유지했습니다. v0.2에서는 원본 파일을 수정하지 않고 메타데이터와 검사 도구를 추가했습니다.
  • v0.1 was frozen and left alone. The client manifest, three non-IID allocations, 23 evaluation prompts, 10 public source texts and the decoding settings were fixed in v0.1. v0.2 layers metadata and tooling on top without modifying any of those files.
  • 난수 시드와 설정을 따로 기록했습니다. 실행에 쓰인 모든 시드를 한 파일에 모으고, 비교 대상 방법들이 같은 연산 자원을 쓰도록 설정 스냅샷을 남겼습니다. 조건이 달랐던 비교는 나중에 되짚을 수 있어야 합니다.
  • Seeds and configurations are recorded separately. Every seed used in a run is collected in one file, and a config snapshot records that compared methods were given the same compute. A comparison run under uneven conditions has to be traceable later.

재현성Reproducibility

  • v0.1에서 v0.2를 재생성하는 스크립트를 작성했습니다. 고정한 v0.1 파일에 변환을 다시 적용하고 현재 v0.2 파일과 비교해 결과가 일치하는지 확인합니다. 기존 파일은 덮어쓰지 않습니다.
  • v0.2 can be rebuilt from v0.1. The rebuild script reads the frozen v0.1 files, reapplies the v0.2 transformation and compares the result with the current v0.2 files — comparing, never overwriting. Matching output means the benchmark reconstructs deterministically.
  • 파일 50개의 SHA-256 체크섬을 관리합니다. 중요한 파일 전부의 체크섬을 한 목록에 두고, 표준 명령으로 검증할 수 있게 했습니다. 누군가 파일을 고치면 무결성 검사에서 바로 드러납니다.
  • SHA-256 checksums cover 50 files. Every critical file's checksum sits in one manifest, verifiable with a standard command, so any edit surfaces immediately in the integrity check.
  • 버전과 변경 이력을 남겼습니다. 버전 파일과 변경 기록을 두어, 어떤 실험 결과가 벤치마크의 어느 버전에서 나온 것인지 뒤에 확인할 수 있게 했습니다.
  • Version and change history are kept, so any result can later be traced to the benchmark version that produced it.
